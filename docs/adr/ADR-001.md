# ADR-001 — Adoção da arquitetura e stack tecnológica do Connexa

- **Situação:** aceita
- **Data:** 2026-11-03
- **Participantes:** Arthur Yhago Santos Lima, Cauã Lopes Simões, Gustavo Gomes de Azevedo, Gabriel Monteiro Marques

## Contexto

O projeto Connexa necessita de uma arquitetura que permita o desenvolvimento organizado de suas funcionalidades, facilitando a manutenção, os testes e a evolução do sistema durante as sprints.

Considerando o contexto acadêmico, o prazo de desenvolvimento, o trabalho em equipe e a necessidade de integração entre os componentes da aplicação, foi necessário escolher uma arquitetura e tecnologias que oferecessem organização, produtividade e facilidade de manutenção.

Também foi considerado o template disponibilizado para Node.js, que fornece uma estrutura inicial com ferramentas de desenvolvimento, banco de dados, testes automatizados e integração contínua.

## Decisão

A equipe decidiu adotar uma arquitetura de monólito modular no back-end, utilizando Node.js com TypeScript e NestJS, integrada a uma aplicação front-end em React. Para persistência dos dados, será utilizado PostgreSQL, com gerenciamento de acesso e migrações por meio do Prisma.

A aplicação será organizada em módulos independentes, respeitando suas fronteiras e responsabilidades, permitindo que as funcionalidades sejam desenvolvidas e testadas separadamente.

**Stack tecnológica adotada:**

- **Back-end:** Node.js 24, TypeScript e NestJS 12.
- **Front-end:** React 19, TypeScript e Vite.
- **Banco de dados:** PostgreSQL 17.
- **ORM e migrações:** Prisma 7 e Prisma Migrate.
- **Testes:** Vitest, Supertest e Testing Library.
- **Qualidade de código:** ESLint e eslint-plugin-boundaries.
- **Ambiente de desenvolvimento:** GitHub Codespaces e Docker.
- **Integração contínua:** GitHub Actions.

## Alternativas consideradas

| Alternativa                                | Por que não foi escolhida                                                                                                      |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| Arquitetura de microsserviços              | Apresenta maior complexidade de configuração, comunicação e manutenção, não sendo necessária para o escopo inicial do projeto. |
| Monólito tradicional sem separação modular | Pode dificultar a organização do código e aumentar o acoplamento entre funcionalidades conforme o sistema cresce.              |
| Java ou .NET no back-end                   | São alternativas tecnicamente viáveis, mas a equipe optou pelo template disponibilizado em Node.js e TypeScript.               |

## Consequências

- **Positivas:** organização do código em módulos, facilidade de manutenção, possibilidade de desenvolvimento paralelo entre integrantes, reutilização de ferramentas, testes automatizados e integração contínua. A utilização de TypeScript também contribui para a identificação de erros durante o desenvolvimento.

- **Negativas:** a equipe precisará respeitar as regras de separação entre módulos, aprender e manter diferentes tecnologias e bibliotecas. Além disso, por ser um monólito, os módulos não possuem implantação e escalabilidade independentes.

- **Como verificar:** a decisão será verificada por meio dos testes automatizados, das regras de fronteira entre módulos configuradas no ESLint, do teste de arquitetura e dos checks de integração contínua do GitHub Actions. As revisões de Pull Requests também deverão verificar se a organização modular e a stack definida estão sendo respeitadas.
